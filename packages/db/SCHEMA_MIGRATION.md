# Schema migration notes

Migration `20261108000000_align_usecase_schema` creates the eight guide-defined business tables with snake_case physical names and `BIGINT GENERATED BY DEFAULT AS IDENTITY` keys. It runs a preflight before renaming any source tables and aborts the migration if a row cannot satisfy the documented types or constraints. The old tables are retained as `legacy_*` archives with an added `_migration_new_id` column; original columns and records remain intact, and no source record or source password hash is deleted.

## Mapping

| Legacy table/field | New table/field | Conversion |
| --- | --- | --- |
| `Agent.id`, `username`, `passwordHash` | `user.user_id`, `username`, `password_hash` | New numeric IDs are assigned in lexical order of the old text IDs; hashes and usernames are copied as stored. |
| `Owner.id`, `agentId`, `name`, `phone` | `owner.owner_id`, `user_id`, `name`, `phone` | Both IDs are translated through the user/owner ID maps. |
| `Property.id`, `agentId`, `ownerId`, common fields | `property.property_id`, `user_id`, `owner_id`, common fields | IDs are translated; Thai statuses `ว่าง`, `กำลังดำเนินการ`, `ขายแล้ว` map to `available`, `in_progress`, `sold`. `area` and `price` become `NUMERIC(12,2)` and `NUMERIC(14,2)`. |
| `Customer` | `buyer` | Renamed entity; user and buyer IDs are translated, and nullable budget/income values become `NUMERIC(14,2)`/`NUMERIC(12,2)`. |
| `Appointment` | `appointment` | User, owner, customer, and property IDs are translated. Thai types/statuses map to `viewing`/`transfer` and `scheduled`/`completed`/`cancelled`. Legacy naive timestamps are interpreted as UTC instants and stored as `TIMESTAMPTZ`. |
| `PropertyTask` | `property_task` | ID/property ID, step name, and order are translated/copied. Legacy `status` and `completedAt` remain available in `legacy_property_task` because they are outside the guide's four-column business table. |
| `PropertyPosting` | `publication_check` | `website` becomes `website_name`; `ลงแล้ว` maps to true and requires a timestamp, `ยังไม่ลง` maps to false with NULL `published_at`. |
| `PropertyStatusHistory` | `property_status_history` | IDs are translated, statuses mapped to canonical English values, old `changedBy` retained as `changed_by`, and naive timestamps interpreted as UTC. |
| `AgentSession` | unchanged infrastructure table | Preserved with its original FK to `legacy_agent`. The new auth flow uses signed cookies and does not consume these old text-ID sessions; agents must sign in again. Session rows are retained, not deleted. |

Numeric IDs are generated by `row_number() OVER (ORDER BY legacy_text_id)` per entity, making the mapping deterministic for the retained legacy rows. The exact correspondence is also persisted in each archive table's `_migration_new_id` column; temporary lookup tables use those values to remap foreign keys during migration. Identity sequences are advanced after backfill to avoid collisions with subsequent inserts.

## Preflight and preservation

Preflight rejects invalid usernames/hashes, malformed names/phones, unsupported property/appointment types or statuses, missing required appointment buyer/property links, cross-agent relationships, invalid timestamps, unsupported history transitions, publication flag/time mismatches, and numeric values that exceed the target precision or require rounding. A failure rolls back and leaves the original tables untouched. Resolve the specific source rows before retrying; do not delete or merge them to make the migration pass.

## Validation performed

- `prisma validate` passed for the new schema.
- `prisma migrate deploy` applied all five migrations, including the new migration, to an isolated empty PostgreSQL database.
- A seeded isolated PostgreSQL fixture with legacy CUID IDs, Thai statuses, a password hash, a leading-zero phone, decimal amounts, appointment/publication timestamps, a task, and status history passed. It checked source/canonical row counts, archive ID mappings, canonical values, preserved hash/phone/decimal values, relationships, and the next generated identity value. This fixture ran immediately before the final FK constraint naming/update-cascade-only edit; the edited migration then passed a fresh empty-database deploy.
- Final `prisma migrate diff` showed no identity-vs-serial drift and no business-table FK drift. It showed index rename suggestions and drops for intentionally unmodeled `legacy_*` archives and `AgentSession`. A future `db push` or schema reconciliation could remove those retained archives, so do not use it as a migration substitute while they remain. No migration was applied to the live project database.

Existing `AgentSession` records are retained, but old sessions are not active under the new signed-cookie authentication; agents must sign in again.
